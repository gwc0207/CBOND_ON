# 因子工程治理规则

> 状态：已落地的因子治理规则。当前 live50 已通过 immutable Catalog
> release 准入；非实盘因子由独立 23:59 research supplement 管理。
>
> 适用范围：当前 canonical 全量 800 个因子实例，以及后续新增因子。其中包括冻结
> research catalog 的 773 个实例，以及与其名称不重叠的 legacy live27 实例。

## 0. 工作前数据盘点、复用与正式口径

### 0.0 需求确认门

对于会改变代码、配置、数据、文件、进程、调度、外部状态或创建长期任务的执行型需求，Agent
必须先输出简洁的需求确认单，等待 Owner 明确确认后，才可进行任务专属的盘点、预检或执行。

需求确认单必须包含：

```text
需求目标与边界
拟采用的工作流，以及将复用或核验的既有数据和服务
预期命令、写入目标、产物、风险等级和验证方式
操作状态：只读 / research-only / no-DB / 影响实盘 / destructive
```

确认只授权已声明的范围。若执行中发现需要新的写入目标、不同的数据合同、额外长期任务或实质
不同的工作流，必须重新说明并等待新的确认。纯回答、解释和 Owner 明确要求的只读状态查验不
需要此门；Owner 明确要求立即执行时，可按其明确范围跳过此门。

### 0.1 先盘点，后操作

任何涉及因子、算子、panel、FactorStore、筛选、实验、模型输入或实盘准入的工作，必须先
完成只读的数据与服务盘点；在盘点结论明确前，不得生成、回填、迁移、重建、删除或启动长期
任务。

盘点必须以实际文件、服务状态和当前配置为准，而不是仅凭默认路径、旧报告、记忆或推测。
至少逐项记录：

```text
数据或服务名称 / 唯一责任写入者 / 实际根目录
覆盖日期 / schema 与 PIT 时间口径 / manifest 或 .done 状态
当前消费者 / 读写权限 / 可复用、缺失和失效分区
```

完整链路必须按以下顺序确认：

```text
上游数据 -> 公共 panel -> label -> 因子结果 -> 模型输入 -> 回测或实盘产物
```

只有完成上述地图后，才可判定某个分区是否真的缺失；配置中声明的路径不存在，不等于同类
数据在本机、既有服务或已发布输入中不存在。

### 0.2 复用优先与唯一责任写入者

对任何输入或中间数据，执行顺序固定为：

```text
验证既有数据和既有服务 -> 复用完整有效分区 -> 仅补齐已证明缺失或失效的分区 -> 验证
```

不得因为“能够重算”而重算已有完整数据。公共数据层由其专属服务写入；下游因子、模型、
实验和实盘任务只能读取已发布输入，并只能写入各自被授权的输出根。不得在下游任务中自行
创建平行的公共数据层、临时服务、临时缓存、日历或报告体系。

优先调用项目已有的服务、工作流和通用入口。只有在数据地图证明既有服务缺少必要能力后，
才可提出最小扩展；扩展的输入、输出、归属、覆盖、清理和报告位置必须在实施前明确。

### 0.3 三种正式因子口径

面向运行、管理、报告、交接和用户沟通，因子只使用以下三种口径：

1. **实盘所需要的因子**：当前实盘 release 精确引用的因子；数量随实盘准入变化。
2. **实验用因子**：当前一次实验精确引用的因子；数量随实验定义变化。
3. **因子库内因子**：已注册于 Factor Catalog 的全部因子。

因子的来源、历史版本、实现语言、筛选状态或曾经使用过的集合，只能作为 Catalog、release、
profile 或实验 manifest 的审计字段，不能形成额外的运行分类或对外口径。因子数量必须从当前
release、实验 manifest 或 Catalog 实际解析，不得以旧数量、旧名称或历史分组推断。

### 0.3.1 三张本地因子结果表与唯一读写入口

本地因子结果只允许存在以下三个正式表根：

```text
D:/cbond_on/factor_store/
  live/                         # 实盘所需要的因子
  experiment/                   # 实验用因子
  factor_library/<family>/      # 因子库内因子，按 primary_family 物理分区
```

每个发布日必须遵守：

```text
parquet -> day manifest -> .done
```

因子库内因子还必须在全部 family bundle 完整后发布该日 logical-day
manifest 与 `.done`。消费者只能经 `factor_table: {table_id, root, families?}`
解析并验证表、合同、manifest 与 `.done`；不得把 `factor_data_root` 的自由路径
作为正常因子输入。

唯一责任写入者为：

1. admitted live runtime 只写 `live`；
2. 被明确实验合同准入的实验 publisher 只写 `experiment`；
3. 23:59 research supplement 只写 `factor_library`，并与同日已发布的 live
   因子合并后再发布完整 logical day。

任何非三表根的因子 parquet 只能在迁移、审计或明确保留的历史复现任务中以显式只读方式
访问；不得作为默认、live、模型、回测、Dashboard 或调度输入，也不得再由普通任务写入。

### 0.4 产物与报告纪律

每项任务必须使用既有的输出合同和实验记录位置。研究输出只写入独立、可审计的
`D:/cbond_on/research_scratch` 根；正式实验记录写入既有 `docs/experiment_records/` 体系。不得
为一次任务随意新建无归属的根目录、报告格式、服务入口或长期 watcher。

## 1. 术语与层级

### 1.1 因子

因子是可以独立评估、独立入模、独立发布的 **因子实例**。每个因子必须有唯一
`factor_id`，即使它与其他因子复用同一套计算逻辑、只在窗口或参数上不同。

当前冻结 research catalog 的 773 个信号，以及 legacy live27 的 27 个实例，均按
此口径视为因子，并必须进入同一个全量因子注册表（canonical total = 800）。773 是
冻结研究来源集，不是全量因子库的上限。是否计算、是否完成验证、是否参与实验、
是否入模型、是否进入实盘，均不影响其因子身份和注册资格。

### 1.2 通用算子

通用算子是可复用的计算能力，不是因子。例如 rolling、rank、z-score、分组、
PIT 日期对齐、共用行情预处理以及 Rust 批量计算 kernel。

通用算子在独立的算子注册表中注册，拥有自己的 `operator_id`、版本、输入输出
契约和测试。一个通用算子可以服务多个因子；一个因子可以组合多个通用算子。

### 1.3 三类引用清单

全量因子注册表之外，只允许以下清单引用已注册因子：

1. 研究 profile：定义一次研究计算、筛选或模型实验使用的因子集合；
2. 模型 feature-set manifest：定义某次训练或回测使用的特征集合；
3. 实盘 release manifest：定义某次实盘允许使用的精确因子集合和版本。

这些清单不能创建因子，也不能修改因子定义；它们只能引用 `factor_id + version +
contract_hash`。

## 2. 因子库管理规则

### 2.1 一因子一份独立定义

每个因子必须有独立目录、定义文件、契约和测试，按主因子族归档：

```text
factor_engine/
  operators/
    <operator_id>/
  factors/
    <primary_family>/
      <factor_id>/
        definition.py
        contract.json
        tests/
```

`definition.py` 是该因子的唯一身份和固定参数入口；它可以调用共享 Python/Rust
算子与 kernel，但不得复制公共数学逻辑。

每个因子必须记录：

```text
factor_id / version / primary_family / tags
definition_path / operator_bindings / fixed_params
input_schema / output_schema / PIT 可见性 / lookback
contract_hash / test_reference / source lineage
```

主因子族用于目录和主分类；`tags` 用于表达跨域属性，避免把股债联动、日频、盘口等
复合因子强行归入唯一语义类别。

### 2.2 全量因子注册

全量因子注册表（Factor Catalog）是因子身份的唯一事实来源。当前必须包含 canonical
800 个因子（`research773` + `legacy_live27`），并对后续新增因子增量管理。每条记录
必须保留 `source_set`，用于说明来源，不用于决定因子地位或是否注册。

注册校验至少要求：

- `factor_id` 唯一且不可复用；
- definition、contract、operator binding 和参数可解析；
- family 与 tags 合法；
- PIT、输入字段和输出列已声明；
- 版本与 contract hash 可复现；
- 同一 `factor_id + version` 不允许公式或参数原地变更。

注册不等于已计算或已进入实盘。运行准备度、Rust 准备度、数据物化、质量评估、模型
引用和实盘发布均作为独立记录保存。

### 2.3 通用算子注册

通用算子不进入因子总表，而进入 Operator Catalog。每个算子必须声明：

```text
operator_id / version / implementation_path / language
input_schema / output_schema / deterministic contract / test hash
```

因子 contract 必须显式列出所依赖的算子及版本。算子升级不得静默改变既有因子结果；
若影响输出，必须产生新的因子版本或经过明确的历史一致性验证。

当前 P0/P1 的 Operator Catalog 已登记全部 266 个静态算子；某个算子暂未被 canonical
800 因子实例引用，不影响它作为算子的注册地位。

## 3. 日内与收盘后计算规则

### 3.1 实盘时间窗

实盘只计算当日实盘 release manifest 所列的因子。当前盘中合同保持：

```text
因子时点：T 日 14:30
标签时点：T 日 14:42（仅研究/训练评估使用）
```

实盘运行时按 release manifest 和每个因子的声明时点按需解析 definition 与通用算子；
不得在启动阶段批量加载或计算未被该 release 引用的因子。

盘中因子只能使用在 14:30 前可见的数据；日频输入必须遵守其声明的严格历史日期
边界。实盘计算只写入 `D:/cbond_on/factor_store/live`，不扫描、加载或覆盖研究
因子数据。

### 3.2 每日研究补算

每日 23:59 补齐全量 Factor Catalog 中未被当天实盘 release 计算的因子。该任务是与
实盘 scheduler 分离的独立 research job，当前 Windows Task Scheduler 名称为
`CBOND_ON_FactorSupplementV1`，只运行单个 score day。

补算的硬约束：

- 先验证 DataHub 当日 manifest 与 `.done` 完整；不完整则 fail-closed 并进入重试队列；
- 对 T1430 因子仍使用原声明的 14:30 信息截面，不能因在 23:59 运行而读取盘后未来数据；
- 将非 live 因子经 ephemeral scratch staging 发布到
  `D:/cbond_on/factor_store/factor_library`；禁止回写、覆盖或合并 live 表；
- 每次运行记录 catalog snapshot、因子版本、输入数据 manifest、完成/缺失清单、每列 hash
  与 coverage；全 NaN 列必须显式告警，不能被记录为无质量问题的正常数据；
- 不得触发模型打分、交易名单、数据库写入或常规实盘 scheduler。

若 23:59 时数据未齐全，任务只允许重试或告警；不得用不完整数据制造“已补齐”状态。

## 4. 实盘准入规则

实盘存在且仅存在一条因子准入路径：

```text
全量 Factor Catalog
  -> live admission
  -> immutable live release manifest
  -> live factor computation
```

实盘 release 的每一个条目必须锁定：

```text
factor_id / factor_version / contract_hash / output_column
operator versions / Rust capability (如适用) / feature order
```

实盘准入只引用因子库中的同一份 definition；不得复制公式、另建同名实盘因子，或让
实盘配置通过通配符扫描全量因子库。任一 release 变更都必须经过独立的 live-change
确认、无 DB dry-run 和一致性校验。

## 5. Rust 规则

1. 当前已存在的 Rust 因子、Rust contract 与实盘 Rust 能力保持原样，作为短期冻结
   的兼容边界；
2. 实盘 release 中的每个因子必须具备对应 Rust 实现与已加载二进制 capability 的
   精确校验；
3. 非实盘因子可以先保留当前可验证的研究实现和身份契约，不要求立即 Rust 化；
4. Rust 化是增量提速工程：先对有明确研究或实盘价值的因子补充 Rust 实现，再做
   Python/reference 与 Rust 输出、NaN、PIT 和历史日度 hash 一致性校验；
5. Rust 化不会改变因子 identity，也不能以替换既有实盘 Rust 实现为捷径。

## 6. 回测规则

除非一次实验明确声明且获得批准，模型与策略回测统一遵守：

```text
起点：2024-01-01
训练方式：连续 rolling OOS
refit：每日 refit
状态：首次训练后连续 warm start
因子时点：T1430 / 14:30
标签：同评分日 14:42
股票池：严格 T-1 o_0005，无无过滤 fallback
交易、mask、成本、benchmark：保持当前既定合同，不得因因子实验改变
```

每次回测必须冻结并记录：

- Catalog snapshot 与 factor_id/version/contract hash；
- feature-set manifest 与特征顺序；
- 训练窗口、warm-start/refit、模型状态来源；
- 因子、标签、卖出窗口、universe、预处理、交易和成本口径；
- 输出根、命令、运行时间、汇总指标和图表。

任何因子或算子变化都必须以新的版本/manifest 参与对照；不得在同一历史回测中混入
未来选择的因子集合，或改变既定交易规则来制造提升。

## 7. 实验规则

### 7.1 因子实验

- 新因子先完成 catalog 注册、单因子机械验证和 PIT 审计；
- 因子定义不得读取 label、未来收益、PnL、模型 score、交易 mask 或实盘数据库；
- 研究报告、模型状态和临时 staging 只能写入 `D:/cbond_on/research_scratch`；
  正式实验因子结果只能由 experiment publisher 写入
  `D:/cbond_on/factor_store/experiment`；
- 单因子报告、筛选和相关性分析仅产生评估证据，不修改因子身份或实盘状态；
- 每个实验记录家族、因子版本、数据区间、输入可见性、结果和失败原因。

### 7.2 模型实验

- 模型实验只能引用 Catalog 中已注册因子；
- 先验证原子模型的独立 rolling OOS，再进行模型间选择或融合；
- 比较必须对齐日期、因子集合、warm start/refit、标签、universe、预处理、交易规则和
  成本；
- 任何研究结论不得自动改变 live release、实盘模型、调度或数据库。

## 8. 迁移约束

当前迁移已完成全量 Catalog、兼容 resolver、live50 release binding、独立补算链和
隔离验证。后续对任一因子定义、通用算子、release 或调度的改变仍必须以新的版本、
manifest、no-DB 验证和明确授权进行；现有 Rust 二进制、模型状态、DB 目标和交易链
保持受保护边界。
